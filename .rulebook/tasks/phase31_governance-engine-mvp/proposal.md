# Proposal: phase31_governance-engine-mvp

## Why
Cortex's "govern" promise (architecture §5.4, PRD goal G5: codify/enforce/audit development laws with graduated punishment) is currently a read API over manually-seeded data, not a live enforcement loop. Specs 13 (Laws DSL, shipped v1) and 14 (governance engine, still 🟡 draft) are the single biggest unbuilt spec surface per `docs/analysis/cortex/06-governance-gap.md` and `docs/analysis/cortex/11-platform-vision-analysis.md` §2.4/§A2. Direct code inspection during this task's planning nailed down the precise shape of the gap: the Claude Code adapter's `PreToolUse` sync path (`crates/cortex-adapter-claude-code/src/sync_paths.rs::SyncClient::law_check`) already POSTs `{tool_name, input, session_id, turn_id}` to `{api_endpoint}/v1/laws/check`, already fails open on timeout/error, already computes `deny = block_on_critical && any(severity == "critical")` (config default `block_on_critical = true`), and the dispatcher already turns `deny` into a real `HookResponse::deny(reason)` (`crates/cortex-adapter-claude-code/src/dispatcher.rs:246-256`). None of that ever fires today because `crates/cortex-api` has **zero dependency on `cortex-laws`** and **no `/v1/laws/check` route exists** — every call 404s/connection-errors and silently fails open. The 72 `LawViolation` nodes visible in Nexus/Meili today came from a one-time bootstrap import of `.claude/rules/*.md`, not a live evaluator, and the dashboard's Laws view (`gui/src/views/Laws.tsx`) and `/v1/dashboard/trust` route are reverse-engineered/stub for the same reason. This task closes that gap with the smallest wiring that makes the existing (already-built) client-side enforcement path real, plus the tier-1/2 punishment ladder and trust score spec 14 defines.

## What Changes
1. **Sync (blocking) evaluation path** — add `cortex-laws` as a dependency of `crates/cortex-api`; load a `LawRegistry` at boot from a configurable directory (empty directory ⇒ empty registry, matching `LawRegistry::load`'s existing behavior, so this is safe to ship with zero laws seeded); implement `POST /v1/laws/check` mapping the request into `cortex_laws::EvalContext`, filtering `LawRegistry::evaluate()` output to `verdict == Deny`, and projecting each `Verdict` into the adapter's already-expected wire shape `{law_id, severity, message}`. Because the shipped v1 `Law` schema has no `mode: blocking|observational` field (that is an unshipped spec-13 future-phase field), this MVP derives "blocking-eligible" purely from `severity == critical` — no schema migration. **Operational note**: `block_on_critical` already defaults to `true` client-side, so the moment this route ships and any `severity: critical` law is loaded, live sessions start being blocked — the starter law set must ship at a lower severity (or empty) until a deliberate follow-up opts a specific law into `critical`.
2. **Async (observational) evaluation + live `LawViolation` write path** — a new consumer (home: `crates/cortex-workers`, per the existing "cortex-workers as the default host for worker-style daemons" precedent) subscribes to the enriched tool-call event stream, runs the same `LawRegistry::evaluate()` for non-critical laws, and on a match POSTs a `law_violation`-kind envelope through the same ingestion path every other producer uses — reusing the existing schema the 72 bootstrap-imported nodes already prove round-trips correctly through Nexus + the per-repo `cortex-<slug>-governance` Meili index (fulltext-worker routing for `Kind::LawViolation` already exists). De-duplicates violations across worker restarts using the same checkpoint-table pattern as ADR-010's `EnvelopeProducer`.
3. **Tier-1/tier-2 punishment ladder** — tier-1 (dashboard annotation) falls out of step 2 for free once step 5 repoints the dashboard; tier-2 (reminder injection) adds a small SQLite-backed reminder store (`cortex-storage::metadata`, mirroring the existing `pre_thinking_feedback` table) keyed by `(session_id, law_id)` with TTL, and wires it into the pre-thinking bundle assembly path so an active reminder surfaces in the offending session's next turn. Tiers 3 (actually blocking) and 4 (router down-weighting) are explicitly deferred — tier 3's mechanism already exists client-side (see Why), so "deferring" it means deliberately keeping the initial law set below `critical` severity, not leaving code unwritten.
4. **Nightly trust-score recomputation** — new SQLite table keyed by `(model, repo)` (same storage precedent as step 3) computing a severity-weighted violation ratio + decision-adherence signal per spec 14, with a nightly batch job and an on-demand single-pair recompute endpoint.
5. **Dashboard Laws view → live engine** — repoint `gui/src/views/Laws.tsx` and the `/v1/dashboard/trust` stub at the new live registry + trust-score reads instead of the violation-envelope-derived catalogue.
6. **Live end-to-end verification** — seed one YAML law (v1's shipped `trigger: {tool, action, args_match}` shape — NOT a TypeScript/Deno detector; that sandbox is explicitly out of scope, still deferred per spec 13) at a non-critical severity with a reproducible trigger, fire it in a real session, and confirm the violation is written + retrievable via `cortex_law_violations`, the tier-2 reminder appears in the next pre-thinking bundle, and the dashboard reflects both.

## Impact
- Affected specs: 13 (`docs/specs/13-laws-dsl.md`, referenced only — no v1 schema change), 14 (`docs/specs/14-governance-engine.md`, this task is the MVP implementation of its enforcement/reminder/trust-score surface); new delta module `governance` added by this task.
- Affected code: `crates/cortex-laws` (consumed, likely no changes needed for severity-only blocking); `crates/cortex-api` (new dependency, new `/v1/laws/check` route, new `ApiState` field for the loaded registry, new dashboard-facing read endpoints); `crates/cortex-workers` (new observational-evaluator consumer); `crates/cortex-storage` (two new SQLite tables: governance reminders, trust score); `crates/cortex-pre-thinking` / `crates/cortex-adapter-claude-code` (reminder read-back into the bundle); `gui/src/views/Laws.tsx` + dashboard trust route.
- Breaking change: NO — additive; `block_on_critical` stays defaulted `true` but has zero effect until a `severity: critical` law is deliberately seeded.
- User benefit: turns the "govern" promise from a read API over manually-seeded fixtures into a real, live enforcement + audit loop — directly relevant since this project's own `AGENTS.override.md` LAW-CORTEX-001/002 are exactly the kind of rule this engine should eventually be able to detect violations of.
