## 2. SQLite tail loop for `.rulebook/memory/memory.db`

- [x] 2.1 New module `crates/cortex-api/src/memory_tail.rs` exposing `MemoryTailWatcher` with `new(db_path: PathBuf, bus: DashboardEventBus)` and `tick_once() -> TickReport`. The bus is taken by value (clone-cheap broadcast sender) instead of `Arc<DashboardEventBus>` because `DashboardEventBus` already implements `Clone` over its underlying `broadcast::Sender`.
- [x] 2.2 `open_ro()` opens with `OpenFlags::SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_URI | SQLITE_OPEN_NO_MUTEX` so concurrent rulebook writes never block. Connection is reopened per-tick rather than stored on the watcher because rusqlite `Connection` is `!Send` and the spawned tokio task that owns the watcher needs to be `Send`. Per-tick reopen is cheap (microseconds) on a local SQLite file and cleanly avoids the `Send`/`Sync` complication.
- [x] 2.3 Per-tick query: `SELECT rowid, id, name FROM memories WHERE rowid > ?1 ORDER BY rowid`. The original §2.3 plan included `type` and `COALESCE(updated_at, created_at) AS ts`; in the actual implementation only `id` and `name` are needed for the `DashboardEvent` payload (the dashboard fetches the full memory record on invalidation). Seeding rule: first tick (cursor = -1) runs `SELECT COALESCE(MAX(rowid), 0) FROM memories` and stamps the result without replaying history.
- [x] 2.4 Emits `DashboardEvent { kind: MemoryAppended, entity_id: row.id, summary: row.name, source: Watcher }` per new row. `last_rowid` updates AFTER iterating the row set so a panic mid-iteration does not advance the cursor past the un-published row.
- [x] 2.5 Wired into `cortex-api/src/main.rs` startup right after the FS watcher block. `CORTEX_DASHBOARD_MEMORY_TAIL` env (default `1`) gates the tail; if set to `0`, the tail loop is not spawned. Per `rulebook_root`, `spawn_tail_loop(root.join("memory").join("memory.db"), bus.clone(), DEFAULT_DEBOUNCE, run_flag)` runs at the same 250 ms cadence as the FS watcher debounce. Missing `memory.db` is a no-op tick (returns the degraded-path `TickReport`).
- [x] 2.6 Integration test `subsequent_tick_emits_event_per_new_row` in `memory_tail::tests`: seeds the schema, inserts one historical row, ticks (seeds cursor without emitting), inserts two new rows, ticks again (asserts 2 `MemoryAppended` events received within 100 ms), then ticks a third time (asserts 0 new rows emitted). Plus `first_tick_seeds_max_rowid_without_replaying_history` confirms the seed rule.
- [x] 2.7 The three degradation tests in `memory_tail::tests` (missing-db, unrecognised-schema, repeat-warning suppression) cover every error path. Schema mismatch / open errors flag boolean `schema_warned` / `open_warned` flags so subsequent ticks suppress repeat logs (rate-limiter via single-flag latching). The watcher never panics — every error path returns the degraded-path `TickReport`.
