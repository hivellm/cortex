# Proposal: phase28_live-testing-bugfixes

## Why
A 2026-07-05 live-verification pass — `cargo check`/`cargo test`/`cargo audit` plus a smoke test against the running Docker Compose stack — surfaced concrete, reproducible defects rather than theoretical ones. Several block confidence in "what already works": a unit-test regression in the embedder's fallback chunker, operator tooling (`cortex-ops doctor`) that is both mis-wired and Windows-incompatible, a graph-worker consumer loop that has been silently stalled for over a week while its container kept reporting "healthy", two dependency CVEs with upgrade paths already identified, and local-stack documentation that describes a fraction of the real 12-service Compose topology. These need fixing before larger roadmap work proceeds so the platform's baseline can be trusted again.

## What Changes

1. **Chunker fallback regression.** `crates/cortex-workers/tests/embedder_it_chunk_pipeline.rs::unknown_language_falls_back` (assertion at line 182) fails because `FallbackChunker::chunk` (`crates/cortex-workers/src/embedder/chunker_fallback.rs`) derives its input text from `event_text()` → `nl_projection()`. For a `Kind::ToolCall` event whose payload carries none of `tool_name`/`input`/`output` (e.g. a bare `"content"` field — exactly what the test's `enriched()` helper builds), the `ToolCall` branch of `nl_projection()` still emits the non-empty placeholder `format!("{tool}({input})")`, i.e. the literal string `"()"`, which short-circuits `event_text()`'s fallthrough to the legacy `content`/`text`/`body` extraction (this is a regression from the phase0 NL-projection change recorded in `.rulebook/PLANS.md`'s 2026-06-22 entry). Net effect: the fallback chunker embeds the 2-character string `"()"` instead of the raw source for any event shape the per-kind projection doesn't recognize. Fix: treat "no recognizable tool-call fields present" as empty output so `event_text()` falls through correctly to the raw source text.
2. **`cortex-ops doctor` package reference.** `bin/cortex-doctor:13` and `bin/cortex-doctor.ps1:14` both invoke `cargo run -q -p cortex-ops -- doctor`, but the workspace has no package named `cortex-ops` — it is a `[[bin]]` target (declared in `crates/cortex-cli/Cargo.toml`) inside the `cortex-cli` package (`crates/cortex-cli/src/bin/cortex-ops.rs`). Both scripts need `-p cortex-cli --bin cortex-ops`.
3. **`cortex-ops doctor` fails natively on Windows.** `crates/cortex-cli/src/bin/cortex-ops/doctor.rs` (~lines 33-37, ~68-72) shells out to system `curl ... -o /dev/null`. `/dev/null` is not a real path on native Windows (the identical idiom works fine inside the project's own Linux-container `Dockerfile` `HEALTHCHECK` lines, e.g. line 174), so every check reports a false failure off-container. Fix with a portable null sink or, preferably, an in-process `reqwest` HTTP call instead of shelling out to `curl` at all.
4. **`cortex-graph-worker` silent stall.** The Nexus-consumer loop (`crates/cortex-workers/src/graph/worker.rs`, the `GraphClientError::TransientError` arm around lines 975-989) logged `"transient nexus error; engaging backpressure"` and, separately, `"periodic schema re-ensure failed"` (`crates/cortex-workers/src/bin/graph-writer.rs:92`) against `http://nexus:15474/cypher`, then went silent for over a week starting 2026-06-27T12:38. Docker's container-level `HEALTHCHECK` (`Dockerfile:173-174`, `curl .../healthz`) kept reporting "healthy" throughout because it only probes liveness of the HTTP endpoint, not consume-loop progress — the staleness was only visible through `cortex-api`'s aggregated `/v1/health`, via the 600-second freshness-degraded threshold (`crates/cortex-health/src/lib.rs:174`, applied in `crates/cortex-workers/src/admin_health.rs:141`). This item is a genuine investigation: root-cause why the backpressure loop never recovered on its own (do not just restart-and-hope, which would mask the bug), then add a supervisor-level "restart on sustained stall" safeguard as defense in depth once the root cause is understood.
5. **Dependency CVEs.** `quinn-proto` is locked at `0.11.14` (needs ≥0.11.15, RUSTSEC-2026-0185: unbounded out-of-order stream reassembly / remote memory exhaustion) and `rmcp` is locked at `0.8.5` (needs ≥1.4.0, RUSTSEC-2026-0189: DNS rebinding in the Streamable HTTP server transport), reached transitively through `reqwest` (0.12, via `vectorizer-sdk`/`synap-sdk`/`nexus-graph-sdk`) and `nexus-protocol` (via `nexus-graph-sdk`) respectively, across every `cortex-*` crate.
6. **Local-stack docs drift.** `docs/specs/03-local-stack.md`'s service map, resource-limit table, and healthcheck section (~lines 30-37, ~138-145, ~154-169) cover only `vectorizer`/`nexus`/`synap`/`meilisearch`/`cortex-api` plus a generic "cortex-workers" placeholder, while the real `docker-compose.yml` defines 12 distinct services (`cortex-api`, `cortex-ingestion`, `cortex-classifier-worker`, `cortex-embedder-worker`, `cortex-fulltext-worker`, `cortex-graph-worker`, `cortex-claude-archive`, `cortex-vectorizer`, `cortex-nexus`, `cortex-synap`, `cortex-meilisearch`, `cortex-reranker`).

## Impact
- Affected specs: `docs/specs/03-local-stack.md` (content reconciled to match the real 12-service stack; no requirement semantics change)
- Affected code: `crates/cortex-workers` (`embedder/chunker_fallback.rs`, `graph/worker.rs`, `bin/graph-writer.rs`), `crates/cortex-cli` (`src/bin/cortex-ops.rs`, `src/bin/cortex-ops/doctor.rs`), `bin/cortex-doctor`, `bin/cortex-doctor.ps1`, `Cargo.lock` (workspace-wide dependency bumps)
- Breaking change: NO — these are bug fixes, an operator-tooling correction, a dependency bump, and a documentation correction; no public API or behavior contract changes
- User benefit: restores a verified, trustworthy baseline (green test suite, working operator tooling on Windows, an understood and defended-against graph-worker failure mode, a clean `cargo audit`, and documentation operators can actually rely on) before further roadmap work is layered on top
