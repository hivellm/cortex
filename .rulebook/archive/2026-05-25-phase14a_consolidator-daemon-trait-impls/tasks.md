## 3. Daemon binary
- [x] 3.1 New `crates/cortex-workers/src/bin/cortex-consolidator.rs` main loop. Subscribes to triggers via Synap consumer group `cortex.consolidator`. (Library half ships in `consolidator/daemon.rs` with TriggerSource trait, ConsolidatorDaemon struct, run_once + run_forever loop, TRIGGER_STREAM constant `cortex.consolidator.triggers`. Bin half adds `Command::Daemon { synap_url, stream, idle_poll_ms }` plus a SynapTriggerSource wrapping the 0.11 pull API with a local AtomicU64 cursor — matches the embedder pattern since Synap has no server-side consumer groups yet.)
- [x] 3.2 Dispatches each trigger to the matching grain. Concurrency: one grain at a time (consolidation is not throughput-sensitive). (run_once matches on Trigger::{SessionEnd,NightlyTopic,DecisionLanded} and routes to the corresponding grain. Sequential await guarantees one-grain-at-a-time. IterationOutcome::{Idle,Dispatched,Failed} surfaces every outcome. Failure path acks the offset but holds the checkpoint write so a poisoned trigger does not block the queue yet also is not recorded as completed on resume.)
- [x] 3.3 Graceful shutdown on SIGTERM: finishes in-flight grain, writes checkpoint, exits 0. (run_forever uses tokio::select on a shutdown future; the in-flight run_once finishes before the loop checks the signal again so producer-checkpoint writes always land. Bin wires Ctrl-C via tokio::signal::ctrl_c plus SIGTERM via tokio::signal::unix::SignalKind::terminate on unix; Windows falls back to the Ctrl-C path. The shutdown Notify is fired from a spawned signal task that the daemon aborts after run_forever returns. 6 unit tests cover empty queue → Idle, per-grain dispatch + checkpoint write, run_forever drain-then-idle-then-shutdown, failure-path acks-without-checkpoint contract.)
- [x] 3.4 Add to `docker-compose.yml` as `cortex-consolidator` service with health check. (New Dockerfile stage `cortex-consolidator` installs procps + uses `pgrep -f cortex-consolidator` as the healthcheck — the daemon does not own an HTTP surface, runtime health surfaces via cortex-api `/v1/health/consolidator` (phase14a §4.1). Compose service depends on synap+cortex-ingestion, mounts the shared `~/.cortex` archive volume, threads SYNAP_BASE_URL+CORTEX_ARCHIVE_ROOT+CORTEX_METADATA_DB env. `docker compose config --services` lists the new service cleanly.)
