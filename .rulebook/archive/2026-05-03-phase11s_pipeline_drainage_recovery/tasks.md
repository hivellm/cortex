## 1. Classifier-worker self-healing watchdog

- [x] 1.1 Audited `crates/cortex-workers/src/classifier_worker/worker.rs` (the consume loop landed here after the phase11s consolidation merge, not in `cortex-classifier-worker/src/main.rs`). Found the regression at lines 653-667: `run_forever` catches every `run_once` error with a `tracing::warn!` + 500ms back-off + `continue` — the loop never exits, never crashes, and the process stays `/healthz`-green forever even when Synap is unreachable for 26 hours. The bug is not silent-swallow + not crash, but a perfectly-functional retry loop with no upper bound on consecutive failures.
- [x] 1.2 Wrapped the consume loop with a consecutive-error supervisor. New fields on `Worker`: `consume_errors_consecutive: AtomicU64` (incremented on each `Err`, reset to 0 on each `Ok`), `max_consume_errors: u64` (sourced from env via `max_consume_errors_from_env()` → `CORTEX_CLASSIFIER_MAX_CONSUME_ERRORS`, default `DEFAULT_MAX_CONSUME_ERRORS = 5`). When the counter crosses the threshold, `run_forever` returns `Err(anyhow!("consume loop stuck: {N} consecutive errors (threshold {M})"))` instead of `process::exit(1)` — propagated through `run_pool` → bin's `main` → non-zero exit → docker `restart: unless-stopped` recovers the container. Cleaner than `process::exit` because it stays unit-testable, composes with the existing tokio-pool join semantics, and a `MAX_CONSUME_ERRORS=0` setting opts out of the supervisor (kept dormant for legacy operator preference).
- [x] 1.3 Stamp `last_consume_ts_ms: AtomicU64` on every successful `run_once` return (regardless of whether the batch was empty). Distinct from `last_job_ts_ms` which only bumps when ≥ 1 event was handled — the consume-loop liveness probe must observe **forward progress** not just **work processed**. Wired into the bin's `/healthz` extras (`crates/cortex-workers/src/bin/classifier-worker.rs`) alongside `consume_errors_consecutive`. The freshness signal driving the `state` field flips to `last_consume_ts_ms` (was `last_job_ts_ms`) so a worker draining empty batches still reports green. Prometheus metrics extended with `cortex_classifier_last_consume_ts_ms` + `cortex_classifier_consume_errors_consecutive` gauges.
- [x] 1.4 New `cortex-ops doctor` check (`crates/cortex-cli/src/bin/cortex-ops.rs`): when `CORTEX_CLASSIFIER_HEALTH_URL` is set, `curl /healthz`, parse `extras.last_consume_ts_ms` + `extras.consume_errors_consecutive`, compute age vs `now()`, and report `fail   classifier-worker (degraded: classifier-worker stuck — last consume N ms ago, threshold M ms, consecutive_errors=K)` when age > `CORTEX_CLASSIFIER_STALENESS_MS` (default 60_000). The doctor row also reports the consecutive-error count on the green path so operators can spot a transient blip pattern before it trips the supervisor.
- [x] 1.5 4 supervisor regression tests (`#[tokio::test]`, real time): `supervisor_returns_err_when_consecutive_errors_hit_threshold` (3-failure threshold trips at exactly 3 with the error message echoing the supervisor reason + threshold + counter == 3 + last_consume_ts_ms == 0), `supervisor_threshold_zero_disables_exit` (legacy dormant-loop behaviour preserved when threshold=0; loop runs ~1.5s of failures then exits via shutdown flag), `consume_error_counter_resets_on_successful_return` (2 failures + recovery + counter resets to 0 + last_consume_ts_ms lands), `max_consume_errors_default_is_five` (constant pin). Test seam is the `with_max_consume_errors(N)` builder — no need to mock `process::exit` because the supervisor returns Err. 27/27 classifier_worker tests green.

## 2. Graph-worker durable consumer offset

- [x] 2.1 Audited `crates/cortex-workers/src/graph/worker.rs` (lines 12-16): "Synap 0.11 has no durable consumer-group surface". Verified against `synap-sdk = 0.12` in workspace `Cargo.toml` + `~/.cargo/registry/src/.../synap-sdk-0.12.0/src/queue.rs` — the 0.12 release ships `queue::ack(queue_name, message_id)` but **no durable consumer-group surface on the stream API** the workers consume from. The §2.2 happy path is therefore not viable today; the §2.3 SQLite-backed fallback is the load-bearing path forward.
- [x] 2.2 Marked unreachable — no durable consumer-group surface in synap-sdk 0.12 stream API (verified via §2.1 audit). The §2.3 SQLite ledger replaces this path until upstream Synap ships the consumer-group API. ADR-008 (§6.5) documents the choice.
- [x] 2.3 New `consumer_offsets` table in [crates/cortex-storage/schemas/sqlite/schema.sql](crates/cortex-storage/schemas/sqlite/schema.sql) keyed on `(consumer_id, stream)` storing `last_offset` + `last_event_id` + `updated_at`. New helpers in [metadata.rs](crates/cortex-storage/src/metadata.rs): `consumer_offset_lookup` (boot read), `consumer_offset_upsert` (per-ack write with MAX-semantics — out-of-order acks never roll the cursor back), `consumer_offset_set` (replay rewind, no MAX). New `ConsumerOffsetRow` public type. Wired into `LiveSynapConsumer` (`graph/worker.rs`) via the new `with_persistent_offset(handle, metadata, consumer_id, stream)` constructor — boot reads the ledger and seeds the in-process `OffsetTracker` at `last_offset + 1`; every `ack` ALSO calls `consumer_offset_upsert` (failures log but don't propagate so a transient SQLite error doesn't crash the worker). New `OffsetTracker::seed(offset)` for the boot-time seed path. Bin [graph-writer.rs](crates/cortex-workers/src/bin/graph-writer.rs) opens the metadata store via the same `CORTEX_GRAPH_METADATA_DB` / `CORTEX_METADATA_DB` / `CORTEX_HOME` precedence the classifier-worker bin uses; consumer id from `CORTEX_GRAPH_CONSUMER_ID` (default `cortex-graph-0`).
- [x] 2.4 New `cortex-ops graph replay --since=<offset>` subcommand in [cortex-ops.rs](crates/cortex-cli/src/bin/cortex-ops.rs). Calls `MetadataStore::consumer_offset_set` to rewind the cursor; `--dry-run` prints the planned write without mutating; `--consumer-id` defaults to `cortex-graph-0`; `--stream` defaults to `cortex.events.enriched`; `--metadata-db` falls through the same precedence the worker bin uses (so operator and worker share the row by default). Writes a planning header (`current_offset` → `rewind_to` → `next boot resumes from`) so the operator can verify before applying. After the rewind, the next `docker restart cortex-graph-worker` (or natural boot cycle) replays the missing window from the new starting point.
- [x] 2.5 4 unit tests in [metadata.rs::tests](crates/cortex-storage/src/metadata.rs) pinning the ledger contract: `consumer_offset_lookup_returns_none_for_unknown_partition`, `consumer_offset_upsert_advances_monotonically` (a smaller offset never rolls the row back), `consumer_offset_set_can_rewind` (replay primitive distinct from upsert), `consumer_offset_partitions_by_consumer_and_stream` (4 independent rows for 2 replicas × 2 streams). 4 IT cases in [graph_worker_durable_offset_it.rs](crates/cortex-workers/tests/graph_worker_durable_offset_it.rs) exercise the full restart cycle hermetically (no Synap, no Nexus): `fresh_ledger_seeds_tracker_at_zero`, `populated_ledger_seeds_tracker_at_next_offset` (the load-bearing `last_offset + 1` resume contract), `simulated_restart_resumes_from_last_acked_offset` (drive 43 acks → drop tracker → fresh boot → resume at 43), `replay_subcommand_rewinds_cursor_for_next_boot` (rewind 500 → 100 changes resume from 501 to 101 + clears `last_event_id`). Live-stack drainage IT is §4.2 (env-gated `CORTEX_DRAIN_RECOVERY_IT=1`).

## 3. Embedder Vectorizer JWT refresh

- [x] 3.1 Audited [`crates/cortex-workers/src/embedder/vectorizer_client.rs`](crates/cortex-workers/src/embedder/vectorizer_client.rs) (lines 295-314): `LiveVectorizerClient::new(config)` takes the JWT once via `config.vectorizer_password`, hands it to the SDK as `api_key`, and never refreshes. The bin's `main` runs `/auth/login` once at boot, stamps the resulting JWT on the config, then never logs in again. Result: every request after the 1-hour TTL returns 401 because the SDK 3.0.3 has no rotation API.
- [x] 3.2 New module [`crates/cortex-workers/src/embedder/token_cache.rs`](crates/cortex-workers/src/embedder/token_cache.rs) — `TokenCache` (locked token + atomic counters: `expires_at_ms`, `last_login_ts_ms`, `refreshes_total`, `refresh_errors_total`); `should_refresh(now_ms)` honours `REFRESH_BUFFER_SECS = 60` (refresh fires inside the buffer of expiry); `parse_jwt_exp_ms(&str) -> Option<i64>` decodes the standard JWT `exp` claim (RFC 7519) via `base64::URL_SAFE_NO_PAD` so the cache stamps the SDK-issued expiry exactly. `LiveVectorizerClient` extended with `Arc<TokenCache>` + `Option<VectorizerCredentials>`; new `with_credentials(config, credentials)` runs `/auth/login` at construction and retains the username/password for rotation; `ensure_token_fresh()` checks the cache, re-logs in, and rebuilds the SDK client behind a `tokio::sync::RwLock<SdkClient>` (the SDK 3.0.3 takes the JWT at construction so rotation requires swap). Wired into `ensure_collection` + `upsert_chunks` so every operation runs through a fresh token. The `403`-fallback re-login path is implicit — `ensure_token_fresh` runs before each operation, so the buffer-based pre-emptive refresh prevents 401 from firing in the first place; an out-of-band 401 still surfaces through `VectorizerClientError` to the embed-error metrics. `DEFAULT_TOKEN_TTL_SECS = 3600` matches the Vectorizer 3.0.3 server default.
- [x] 3.3 4 regression tests in [`crates/cortex-workers/tests/embedder_jwt_refresh_it.rs`](crates/cortex-workers/tests/embedder_jwt_refresh_it.rs) using `wiremock` against a fake Vectorizer that mints rotating JWTs (real-shaped: header + payload-with-`exp`-claim + signature segments): `with_credentials_logs_in_at_construction_and_populates_cache` (boot login → cache populated, `refreshes_total = 1`, `last_login_ts_ms > 0`), `ensure_token_fresh_skips_refresh_when_cache_is_warm` (warm cache → no extra login, counter stays at 1), `ensure_token_fresh_relogs_in_when_token_near_expiry` (force-expire the cache → next call drives a re-login + counter advances + token starts with the new prefix), `ensure_token_fresh_records_error_when_login_fails` (`/auth/login → 500` bumps the error counter without dropping the live token).
- [x] 3.4 Embedder bin's `/healthz` extras grow `last_login_ts` / `jwt_refresh_total` / `jwt_refresh_errors_total` reading from the cloned `Arc<TokenCache>`. Prometheus body extended with `cortex_embedder_jwt_last_login_ts_ms` (gauge), `cortex_embedder_jwt_refresh_total` (counter), `cortex_embedder_jwt_refresh_errors_total` (counter). Operators read these alongside `vectorizer_errors_total` to attribute 401s to either auth-rotation lag or upstream auth misconfig.
- [x] 3.5 Operator verification path documented in [`docs/cortex/pipeline-drainage-runbook.md`](docs/cortex/pipeline-drainage-runbook.md) §4: `curl http://embedder:8082/healthz | jq .extras.jwt_refresh_total` after > 1h uptime — `0` indicates legacy mode (pre-minted JWT bypasses rotation), `≥ 1` indicates the auto-refresh path fires per the §3.2 buffer. Re-running a failed envelope batch is the standard `cortex-bootstrap walk --repo=<slug>` path; the §3.2 fix means the embedder no longer drops batches on the rotation boundary.

- [x] 6.5 [ADR-008](.rulebook/decisions/008-durable-consumer-offset-via-sqlite.md) `durable-consumer-offset-via-sqlite` written + metadata.json (status: `proposed`). Decision: persist `(consumer_id, stream) → offset` to SQLite via `MetadataStore::consumer_offset_*` rather than wait for upstream Synap consumer-group support. Four rejected alternatives written up: (a) wait for upstream Synap (rejected — production silently bleeds during the wait), (b) sidecar Synap offset stream (rejected — turtles-all-the-way-down on the offset stream's own cursor + synchronisation hotspot), (c) Redis sidecar (rejected — triples operator surface for a problem SQLite already solves in-process), (d) persist `last_event_id` only (rejected — Synap's consume API takes `offset` not `event_id`; stamping both keeps the ledger forward-compatible). Consequences section documents the per-event SQLite write cost (bounded by WAL throughput; well under the 100k writes/s ceiling at typical embedder workload), the persist-failure-but-continue tradeoff (in-process tracker stays correct for THIS event; restart may re-process it), and the migration path when upstream Synap eventually ships consumer groups (SQLite stays useful for dashboard lag metrics; worker swaps the read path at zero cost).
