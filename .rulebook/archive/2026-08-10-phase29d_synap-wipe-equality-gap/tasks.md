- [x] 1.3 UNBLOCKED and shipped — synap#257 landed in **1.3.1** (SDK + image, both pinned): `StreamStats` gained `generation` ("identity of this incarnation of the room: strictly increasing across every room creation, including server restarts") and `created_at`. Verified against the live server before writing any code: a fresh room reported `generation=1786309568829`; after `docker restart cortex-synap` the same room reported `1786309794656` — the wipe is now directly observable. All four consumers switched to the definitive rule: remember `last_seen_generation` beside the cursor (per-room in the classifier); on the bounded stats probe, a CHANGED generation ⇒ wipe ⇒ warn + cursor reset to 0 (+ graph durable `consumer_offset_set` rewind); an unchanged generation never resets a healthy cursor; the first observation only records. The interim `total_published`-decrease bookkeeping is DELETED. One documented concession: when `generation == 0` (server older than 1.3.1, `#[serde(default)]`) the phase29c `cursor > head_next` comparison is retained as a strictly-weaker fallback so a stale deployment cannot silently regress to the original starvation bug.

  **§1.3b — durable-cursor boot gap, found by live validation (not by review or by the unit suite, which was green).** The graph consumer is the only one whose cursor OUTLIVES the process. With the generation baseline held only in memory it was `None` on the first probe after every restart, and a first observation cannot prove a wipe by itself — so the worker adopted the live generation while still pointing into the previous incarnation's dead offset space and sat at `jobs=0` forever (observed: `resume_at=1` against a wiped room whose head was also 1 — the exact tie again). The generation must therefore be as durable as the cursor it qualifies: `consumer_offsets` gained a `room_generation` column (additive `pragma_table_info` migration, `DEFAULT 0` = unknown), plus `MetadataStore::consumer_offset_generation_set`; the graph consumer restores it as its boot baseline and writes it on every observation. Regression test: `persisted_generation_lets_a_durable_cursor_detect_a_wipe_on_the_first_boot_probe` (ledger at generation 7, live room at 99 with the head tied to the cursor → the FIRST probe heals). `persist_generation` also logs write/poison failures instead of swallowing them with `let _ =`, matching the flush path — a silent no-op on a repair path is invisible until the next boot resumes with a stale baseline.

  **Live proof of the whole loop** (graph worker, zero worker restarts needed for the heal itself): boot restored baseline `1786320721740` from the ledger → synap restarted (rooms wiped, live generation `1786327481834`) → the first probe logged `room generation changed since last probe (synap wipe); self-healing cursor to 0 stale_offset=1 prev_generation=1786320721740 new_generation=1786327481834` → the ledger force-rewound to offset 0 AND adopted `1786327481834` (matching the live room exactly, written 1 ms after the warn). An earlier equality-case run likewise carried probe `01KZMG69SNAYJ0AWHY2SF9QGND` through to the graph after the heal.

## 3. Note for the next reader
The unit suite was green BEFORE §1.3b existed — the gap only appeared when the change ran against the live stack, because it lives in the difference between an in-memory cursor (reset by a restart) and a durable one (which is not). Worth remembering when a self-heal is added to a consumer that persists its position: whatever qualifies the cursor must be persisted with it.
