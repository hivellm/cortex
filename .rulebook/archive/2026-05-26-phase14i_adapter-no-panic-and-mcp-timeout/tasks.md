## 2. MCP timeout structured error
- [x] 2.1 Wrap every tool's `call()` body with `tokio::time::timeout(MCP_TOOL_TIMEOUT, ...)`. — Wrapped at the single dispatch site (`Server::handle_tools_call`) instead of inside every `impl Tool` body. The dispatcher already routed through `tokio::task::spawn(run_tool(...))`; phase14i wraps that join handle in `tokio::time::timeout(ctx.tool_timeout(&name), join)`. This covers every present + future tool with one edit, avoids the 14-tool drive-by edit storm, and the timeout always cancels the tool task (no leaked workload).
- [x] 2.2 On timeout, return `ToolError::Timeout { elapsed_ms, tool, request_id }`. The MCP transport surfaces it as a structured error to the host. — New `cortex_mcp_server::tools::reasons::TOOL_TIMEOUT = "tool_timeout"`. New `ToolError::timeout(tool, elapsed_ms)` constructor. Dispatcher emits `error.code = -32603` + `error.data = { reason: "tool_timeout", elapsed_ms, tool, request_id }` on expiry. The `request_id` field carries the JSON-RPC `id` from the request so the host correlates the timeout with the originating call.
- [x] 2.3 Default `MCP_TOOL_TIMEOUT = 5_000` ms; per-tool overrides via `cortex_config::MCPConfig`. — `MCP_TOOL_TIMEOUT_MS = 5_000` const lands in `tools.rs`. `ToolContext` gains `tool_timeout_default: Duration` + `tool_timeouts: BTreeMap<String, Duration>` + accessor `tool_timeout(name)` + builder methods `with_tool_timeout(name, dur)` + `with_default_tool_timeout(dur)`.
