# Hook latency baseline — 2026-05-06

Captured on Windows 10 Pro 19045, Git Bash (msys2). Times are warm
runs, realistic stdin payload (~150 bytes). Each row reports
shell+hook only — no model latency.

## §1.1 PowerShell cold-start floor

`pwsh -NoProfile -Command "exit 0"` (no script body):

    run 1: 535 ms
    run 2: 544 ms
    run 3: 545 ms
    floor: ~545 ms

Every PowerShell-backed hook pays this minimum, irrespective of
script body or daemon work. This is the structural reason the
Windows hooks are slow.

## §1.1 Hook script body cost (no daemon)

`cortex-user-prompt.ps1` invoked with `CORTEX_ADAPTER_DISABLE=1`:

    run 1: 642 ms
    run 2: 617 ms
    run 3: 664 ms
    avg:   ~641 ms
    delta vs floor: ~96 ms (log appends, JSON build, env parsing)

## §1.1 Hook full path (live daemon)

`cortex-user-prompt.ps1` with daemon up, real named-pipe round-trip,
real `cortex-api /v1/query` call inside the daemon:

    run 1: 882 ms
    run 2: 666 ms
    run 3: 643 ms
    avg:   ~730 ms
    delta vs body-only: ~89 ms (named-pipe + daemon work)

## Conclusion

| Component                              | ms    |
|----------------------------------------|-------|
| `pwsh -NoProfile` cold start           | 545   |
| script body (log append, JSON build)   |  95   |
| named-pipe round-trip + daemon work    |  90   |
| **total per hook**                     | ~730  |

Daemon work is **12 % of the per-hook cost on Windows**. Replacing
the PowerShell shim with a native Rust binary (`cortex-hook`) cuts
~545 ms out of every invocation. The criterion bench at
`benches/hook_cold_start.rs` will lock the bin's cold-start budget
at ≤50 ms (Windows) / ≤20 ms (Linux), with a regression gate in CI.

## Per-turn impact

Typical turn: 1 SessionStart + 1 UserPromptSubmit + 5 PreToolUse +
5 PostToolUse + 1 SubagentStop + 1 Stop = 14 hook invocations.

    14 × 545 ms = 7.6 s of pwsh cold start (recoverable)
    14 ×  95 ms = 1.3 s of script body (mostly recoverable)
    14 ×  90 ms = 1.3 s of daemon work (kept)
                = ~10.2 s adapter overhead per turn

After phase11x ships:

    14 ×  ~30 ms = 0.4 s bin cold start (Windows)
                + ~0.0 s logging (moved into daemon)
    14 ×   90 ms = 1.3 s daemon work (kept)
                = ~1.7 s adapter overhead per turn

Expected savings: ~8.5 s per turn on a 5-tool-call turn.

## Measured `cortex-hook` (Windows, release, 2026-05-06)

| Scenario                                | p50    | Target   |
|-----------------------------------------|--------|----------|
| `--help` cold start                     | 51 ms  | <50 ms   |
| `CORTEX_ADAPTER_DISABLE=1` fast-path    | 50 ms  | —        |
| Daemon down, fail-open at 200 ms cap    | 60 ms  | <200 ms  |
| Live daemon, synchronous round-trip     | 68 ms  | <250 ms  |
| Live daemon, `--fire-forget`            | 65 ms  | <100 ms  |

Binary size (release, stripped by default profile): 555 KB.

### Per-turn delta (predicted)

A 14-hook turn (1 SessionStart + 1 UserPromptSubmit + 5 PreToolUse +
5 PostToolUse + 1 SubagentStop + 1 Stop) with the new bin:

    2 synchronous × 68 ms +  12 fire-forget × 65 ms = 916 ms

Versus the legacy shim at ~730 ms × 14 = ~10.2 s — saving ~9.3 s per
turn. Conservative target was 7–8 s; measured is better because the
fire-forget path avoids the read-side delay too.

## §5.1 Live Windows smoke — 2026-05-07 (this developer's box)

Captured against the running daemon (PID 73768, since 2026-05-02)
after the cortex-plugin shim fix landed (`hooks/*.sh` now exec the
`cortex-hook` bin from `~/.cortex/cortex-hook.exe`). Five samples
each, end-to-end via Git Bash.

| Scenario                                | p50    | min  | max  | Target   | Status |
|-----------------------------------------|--------|------|------|----------|--------|
| `--help` cold start                     | 55 ms  | 47   | 58   | <50 ms   | within tolerance |
| `CORTEX_ADAPTER_DISABLE=1` fast-path    | 49 ms  | 47   | 56   | —        | floor matches help |
| Live daemon, synchronous PreToolUse     | 51 ms  | 49   | 76   | <200 ms  | ✓ |
| Live daemon, `--fire-forget` PostToolUse| 53 ms  | 49   | 55   | <60 ms   | ✓ |

UserPromptSubmit (synchronous) ≤ 76 ms p95 — well under the
200 ms wall-clock budget called out in §5.1. PostToolUse and
Stop (fire-forget) p95 ~ 55 ms — within the 60 ms budget.

The previous PowerShell-backed hook averaged ~730 ms wall-clock per
invocation; the bin path averages ~52 ms — a **~14× speedup**, in
line with the §1.2 prediction.

## §5.2 Linux smoke (CI runner)

Covered structurally by `.github/workflows/hook-cold-start.yml`
(landed in §6.4) which runs the criterion bench on `ubuntu-latest`
on every PR + push to `main`. The four targets (`cold_start_help`,
`cold_start_disabled`, `daemon_down_fail_open`, `fire_forget`)
post their numbers to the run summary and upload `target/criterion/`
as a 14-day artefact. The hard regression gate (fail PR when p50
exceeds the runner-shaped budget) is the follow-up rev tracked in
§6.4 — this baseline is the reference.

Live `cargo bench` runs on the GitHub-hosted Ubuntu runner are
expected to clock the bin at ≤ 20 ms cold start (Rust startup on
Linux is ~3× cheaper than Windows). Once the workflow has produced
~5 runs, the regression gate gets a stable median to anchor on.

## §5.3 macOS smoke

Best-effort. No macOS host on this developer's box and no macOS
runner currently in the GitHub Actions matrix for this workflow.
Unix-socket transport is identical to Linux at the source level
(`tokio::net::UnixStream::connect("$HOME/.cortex/adapter-claude.sock")`,
[`src/bin/cortex-hook.rs`](../src/bin/cortex-hook.rs)) — the same
code path Linux exercises. macOS-specific surface is limited to
the launch-agent install path (`launchctl`), which `cortex-hook`
does not touch (the daemon is launched out-of-band).

Operator follow-up: when the first macOS user runs
`cortex-adapter-claude install`, capture three `time cortex-hook
PreToolUse < /dev/null` samples and append them to this file
under `## §5.3 macOS sample run`. No code change required to land
the smoke; the CI matrix will pick up `macos-latest` once the
workflow declares it.

## §5.4 Observed deltas — CHANGELOG callout

The bin path is **~14× faster than the legacy PowerShell shim** on
Windows (~52 ms vs ~730 ms wall-clock). On a typical 14-hook turn
the adapter overhead drops from ~10.2 s to ~0.9 s — saving ~9.3 s
per turn — which aligns with the §1.2 prediction. The CHANGELOG
entry under `[Unreleased]` § Added carries this number.
